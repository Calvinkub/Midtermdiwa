# 📖 สรุปละเอียดแบบเข้าใจง่าย — Building LLM-Powered Applications (L1–L6)

> เขียนแบบ **"เด็กหลังห้องที่ไม่ได้ตั้งใจเรียนก็อ่านรู้เรื่อง"** · ภาษาไทยเยอะ · ตัวย่อทุกตัวมีคำเต็ม + อธิบายว่าคืออะไร · มีเปรียบเทียบให้เห็นภาพ
> วิชานี้สอน **สร้างแอปที่คุยกับ AI ได้ และตอบคำถามจากเอกสารของเราเองได้** (เหมือน ChatGPT เวอร์ชันที่รู้เรื่องในบริษัท/คอร์สเรา)

---

## 🗺️ ภาพรวมทั้งวิชา (อ่านอันนี้ก่อน จะเข้าใจที่เหลือง่ายขึ้น)

ลองนึกภาพเราจะสร้าง **แอปแชตที่ฉลาด** ขึ้นมา 1 ตัว มันต้องมีชิ้นส่วนพวกนี้ประกอบกัน:

1. **ตัว AI (โมเดลภาษา)** — ตัวที่คิดคำตอบ (L1: คุยกับมันยังไง, สั่งมันยังไง)
2. **ทำให้คำตอบเป็นข้อมูลที่โปรแกรมใช้ต่อได้** (L2: บังคับให้ AI ตอบเป็นรูปแบบที่โค้ดอ่านได้)
3. **เซิร์ฟเวอร์หลังบ้าน** — คอมพิวเตอร์ตัวกลางที่คุมทุกอย่าง (L3)
4. **หน้าจอที่ผู้ใช้เห็น** — และทำให้คำตอบ "พิมพ์ออกมาทีละคำ" (L4)
5. **คลังความรู้** — เก็บเอกสารของเราในรูปแบบที่ค้นหา "ความหมาย" ได้ (L5)
6. **การเอาคลังความรู้มาช่วย AI ตอบ** — เรียกว่า RAG (L6)

**คำที่ต้องรู้ก่อนเลย** (จะเจอตลอด):
- **AI / LLM (Large Language Model = โมเดลภาษาขนาดใหญ่)** = โปรแกรม AI ที่เดาคำถัดไปเก่งมาก จนเหมือนคุยกับคนได้
- **Server (เซิร์ฟเวอร์) = เครื่องคอมพิวเตอร์หลังบ้าน** ที่เปิดค้างไว้ตลอด คอยรับคำขอแล้วตอบกลับ (ผู้ใช้ไม่เห็น)
- **Browser (เบราว์เซอร์) = โปรแกรมเปิดเว็บ** เช่น Chrome/Safari ที่ผู้ใช้เห็นและคลิก
- **Frontend (ฟรอนต์เอนด์) = หน้าบ้าน** = ส่วนที่ผู้ใช้เห็นบนหน้าจอ · **Backend (แบ็กเอนด์) = หลังบ้าน** = เซิร์ฟเวอร์ที่ทำงานเบื้องหลัง
- **API (Application Programming Interface = ช่องทางให้โปรแกรมคุยกับโปรแกรม)** = เหมือน "เมนูสั่งอาหาร" ที่บอกว่าขออะไรได้บ้างและจะได้อะไรกลับมา

## 📘 L1 — คุยกับ AI และสั่งงานมันให้ได้ดั่งใจ

### AI จริงๆแล้วทำอะไร? — มันแค่ "เดาคำถัดไป"
AI ตัวนี้ (เรียกเต็มๆว่า **LLM = Large Language Model = โมเดลภาษาขนาดใหญ่**) ทำงานง่ายกว่าที่คิด: **มันเดาว่าคำต่อไปควรเป็นอะไร** แล้วเดาไปเรื่อยๆทีละคำ
- ตัวอย่าง: พิมพ์ "เมืองหลวงของฝรั่งเศสคือ" → มันคำนวณว่า "ปารีส" มีโอกาส 91%, "ลียง" 2% → มันเลือก "ปารีส"
- **ทุกอย่าง** ที่ AI ทำ (คุย, ตอบคำถาม, สรุป, เขียนโค้ด) คือกลไก "เดาคำถัดไป" อันนี้ซ้ำๆ ไม่มีอะไรมากกว่านี้
- **สำคัญมาก 3 ข้อ:**
  1. **มันไม่ได้ "ค้นหา" คำตอบจากฐานข้อมูลในตัว** — ไม่มีตู้เก็บข้อมูลข้างในเลย มันแค่เดาว่าอะไรน่าจะตามมา → เพราะงั้นมันจึง **"มั่ว" ได้อย่างมั่นใจ** (ศัพท์เรียกว่า **hallucination = การหลอน/แต่งเรื่อง**) โดยฟังดูน่าเชื่อพอๆกับตอนที่ตอบถูก
  2. **มันไม่มีความจำ** — คุยจบ 1 ครั้งมันลืมหมด (ศัพท์: **stateless = ไม่มีสถานะ/ไม่จำ**) เราต้องส่งบทสนทนาเก่าให้มันใหม่ทุกครั้ง
  3. **มันมองข้อความเป็น "token" ไม่ใช่ "คำ"** — token คือชิ้นส่วนของข้อความ (ประมาณ 4 ตัวอักษรอังกฤษ = 1 token โดยหยาบๆ) · **ภาษาไทยและโค้ดจะกิน token เยอะกว่า** = แพงกว่า

### เบื้องหลัง AI คืออะไร (ไม่ต้องจำลึก แค่รู้ภาพ)
- AI เป็น **โครงข่ายประสาทเทียม (neural network)** = โปรแกรมที่มีตัวเลขนับพันล้านตัวเรียกว่า **weights (น้ำหนัก)** ไม่มีใครเขียนกฎให้มัน มันเรียนรู้เองจากการอ่านข้อความมหาศาลบนอินเทอร์เน็ต
- สถาปัตยกรรมชื่อ **Transformer (2017)** หัวใจคือ **attention (การให้ความสนใจ)** = ให้แต่ละคำ "มอง" คำอื่นๆรอบตัวแล้วชั่งน้ำหนักว่าคำไหนสำคัญ → นี่คือเหตุผลที่คำว่า "bank" ในประโยค "นั่งริมฝั่ง (bank) แม่น้ำ" กับ "ฝากเงินที่ธนาคาร (bank)" มีความหมายต่างกัน ทั้งที่เป็นคำเดียวกัน — มันดูจากคำข้างเคียง
- AI แชตทั่วไป (GPT, Gemma ที่เราใช้) เป็นแบบ **Decoder-only** = สร้างข้อความทีละคำจากซ้ายไปขวา (อีกชื่อคือ **autoregressive = สร้างต่อจากที่ตัวเองสร้างมา**)

### วิธีคุยกับ AI: ส่งเป็น "รายการข้อความ" ที่มี role (บทบาท)
เราไม่ได้ส่งข้อความดิบๆให้ AI แต่ส่งเป็น **list ของ messages** แต่ละอันมี **role (บทบาท)** 3 แบบ:
- **system (ระบบ)** = กฎ + บุคลิก + รูปแบบคำตอบ → เหมือน "คำสั่งประจำตัว" ที่ตั้งครั้งเดียวใช้ทั้งบทสนทนา (เช่น "คุณเป็นผู้ช่วยที่ตอบสั้นๆ")
- **user (ผู้ใช้)** = สิ่งที่คนพิมพ์เข้าไป
- **assistant (ผู้ช่วย)** = คำตอบเก่าๆของ AI → นี่แหละคือ "ความจำปลอม" ของมัน
- **เพราะ AI ไม่มีความจำจริง** เราจึงต้อง **ส่งบทสนทนาทั้งหมดกลับไปใหม่ทุกครั้ง** ที่ถามต่อ

### สั่งความ "มั่ว/สร้างสรรค์" ของ AI ด้วยปุ่มปรับ (sampling knobs)
AI ให้ "ความน่าจะเป็น" ของแต่ละคำมา เราปรับว่าจะสุ่มยังไง:
- **temperature (อุณหภูมิ) = ปุ่มความมั่ว** · ค่า **0 = ตอบเหมือนเดิมทุกครั้ง (นิ่ง)** เหมาะกับงานที่ต้องการความแน่นอน เช่น ดึงข้อมูล; ค่าสูง (0.7–1.0) = สร้างสรรค์/หลากหลาย เหมาะกับงานคิดไอเดีย
- **top_p (นิวเคลียส) = อีกปุ่มคุมความมั่ว** (เก็บเฉพาะคำที่โอกาสรวมกันได้ p) · **top_k** = ญาติของมัน (เก็บ k คำที่โอกาสสูงสุด)
  - **กฎ: ปรับ temperature หรือ top_p อย่างใดอย่างหนึ่ง ไม่ใช่ทั้งคู่** (มันคือปุ่ม 2 อันที่คุมสิ่งเดียวกัน)
- **max_tokens** = จำกัดความยาวคำตอบ (คุมค่าใช้จ่าย) · **stop** = คำที่เจอแล้วให้หยุดพิมพ์
- เกร็ด: temperature=0 นิ่งมากแต่ **ไม่การันตี 100% เหมือนเป๊ะ** เพราะการคำนวณบนการ์ดจอมีความคลาดเคลื่อนเล็กน้อย

### วิธีเขียน prompt (คำสั่ง) ให้ AI ทำงานดี — 4 แบบหลัก
- **Zero-shot (ยิงตรงๆ)** = ถามเลยไม่มีตัวอย่าง (ใช้กับงานง่ายๆ)
- **Few-shot (ให้ตัวอย่างน้อยๆ)** = โชว์ตัวอย่าง input→output 2–5 อัน แล้ว AI จะ **เลียนแบบรูปแบบ (format)** → นี่คือวิธีที่ดีที่สุดเวลา **รูปแบบคำตอบไม่นิ่ง**
- **Chain-of-Thought (CoT = ห่วงโซ่ความคิด)** = สั่งให้ AI **คิดทีละขั้นก่อนตอบ** → ช่วยงานเลข/ตรรกะหลายขั้นมาก
- **System prompting** = ใส่กฎ/บุคลิก/รูปแบบไว้ใน system message
- **ทำไม prompt ถึงใช้ได้:** เรียกว่า **in-context learning (การเรียนรู้จากบริบทในตอนนั้น)** = AI ไม่ได้ถูกเทรนใหม่ (น้ำหนักมันแช่แข็ง) มันแค่ดูตัวอย่าง/คำสั่งที่เราใส่มาแล้วเดาคำต่อไปตามนั้น → เพราะงี้ "ตัวอย่างดีๆ 2-3 อันชนะกฎยาวเป็นย่อหน้า"

### เครื่องมือ prompt เพิ่มเติม (เลือกใช้ตาม "อาการ")
| อาการที่เจอ | เทคนิคที่ใช้ |
|-------------|--------------|
| ตอบเลข/ตรรกะหลายขั้นผิด | **Chain-of-Thought** (หรือแค่เติม "คิดทีละขั้นนะ") |
| ตอบถูกแต่ห่อด้วยคำพูดเยิ่นเย้อ | **few-shot + บอกรูปแบบชัดๆ + temperature=0** |
| แต่งข้อมูลมั่วอย่างมั่นใจ | **ให้ทางออก** ("ถ้าไม่รู้ให้บอกว่าไม่รู้") + **ป้อนข้อมูลจริงให้ (grounding)** |
| 1 คำสั่งทำหลายอย่างพร้อมกัน | **แตกเป็นหลายคำสั่งต่อกัน (decompose/chaining)** |
| ตอบถูกแต่คุณภาพกลางๆ | **ให้มันวิจารณ์+แก้งานตัวเอง (self-critique)** |
| งานสำคัญที่บางทีพลาด | **self-consistency** = ถามหลายรอบด้วย temp สูง แล้ว **เอาคำตอบที่ได้เสียงข้างมาก** |
| ข้อมูลที่ paste มาแทรกคำสั่งเรา | **คั่นข้อมูลด้วยแท็ก** เช่น `<review>...</review>` (กันการโดนหลอก) |

### Streaming (การส่งคำตอบทีละคำ)
- เพราะ AI สร้างคำทีละคำ เราจึง **ส่งให้ผู้ใช้เห็นทีละคำได้เลย** (ไม่ต้องรอจบทั้งก้อน) — เหมือนพนักงานเสิร์ฟยกอาหารมาทีละจานแทนที่จะรอครบทุกจาน
- **สำคัญ: streaming ไม่ได้ทำให้ AI คิดเร็วขึ้น** เวลารวมเท่าเดิม แค่ **"รู้สึก" ว่าเร็วขึ้น** (ศัพท์: perceived latency = ความหน่วงที่รู้สึก) เพราะเห็นตัวอักษรแรกเร็ว + กดหยุดกลางคันได้

## 📗 L2 — บังคับให้ AI ตอบเป็น "ข้อมูล" ที่โปรแกรมใช้ต่อได้

### ปัญหา: AI ตอบเป็นข้อความ แต่โปรแกรมต้องการ "ข้อมูล"
- แอปต้องการ **ช่องข้อมูลที่ชัดเจน (fields)** เช่น ราคา = 19.99 (เอาไปคำนวณต่อ) ไม่ใช่ประโยค "ราคาคือ 19.99 บาทนะครับ"
- **มองว่า AI คือ "ผู้ใช้แปลกหน้าที่กรอกฟอร์มมา"** = อย่าเชื่อ! ต้องตรวจก่อนใช้เสมอ (ศัพท์: untrusted input = ข้อมูลที่เชื่อไม่ได้)

### JSON คืออะไร?
- **JSON (JavaScript Object Notation = รูปแบบเขียนข้อมูลแบบหนึ่ง)** = วิธีเขียนข้อมูลให้ทั้งคนและโปรแกรมอ่านได้ หน้าตาเช่น `{"item": "มะม่วง", "qty": 3, "price": 45}` (มีคีย์กับค่า อยู่ในวงเล็บปีกกา)
- เราจึงบอก AI ว่า **"ตอบมาเป็น JSON เท่านั้น ห้ามมีคำพูดอื่น"** แล้วเอามาแปลงเป็นข้อมูลด้วยคำสั่ง `json.loads`
- **ห้ามใช้ `eval` เด็ดขาด** — `eval` = สั่งให้ Python รันข้อความนั้นเป็นโค้ด → ถ้า AI (หรือคนไม่หวังดี) แอบใส่โค้ดอันตราย เครื่องเราจะรันให้เลย (ศัพท์: RCE = Remote Code Execution = การรันโค้ดจากระยะไกล ซึ่งเป็นช่องโหว่ร้ายแรง)

### JSON mode และ Schema — "การรับประกัน" 2 ระดับ (และกับดัก)
- **JSON mode** = โหมดที่ provider (ผู้ให้บริการ AI) บังคับให้คำตอบเป็น JSON ที่ **ถูกไวยากรณ์ (syntax)** เท่านั้น — **แต่ไม่รับประกันว่าคีย์/ชนิดข้อมูลถูก**
- **Schema (สคีมา = แบบฟอร์มที่กำหนดว่าต้องมีคีย์อะไร ชนิดอะไร)** = บังคับให้ตรงตามแบบเป๊ะ
- **"JSON ถูกไวยากรณ์ ≠ ข้อมูลถูกต้อง"** (Valid JSON ≠ valid data) — จำประโยคนี้!
- **⚠️ กับดักของวิชานี้:** เซิร์ฟเวอร์ AI ของคลาส (Gemma proxy) **รับคำสั่ง JSON mode แต่ไม่ทำอะไรเลย (เมินเงียบๆ)** → เราจึงต้องพึ่งวิธี **"สั่ง → แปลง → ตรวจ → ซ่อม" (prompt → parse → validate → repair)** เอง

### การตรวจสอบ (validation) — 3 ชั้น
1. **แปลง (parse)** ด้วย `json.loads` → ถ้าไวยากรณ์พังจะ error (ชื่อ error: JSONDecodeError)
2. **ตรวจรูปร่าง/ชนิด (schema/type)** → มีคีย์ครบไหม ชนิดถูกไหม
3. **ตรวจความสมเหตุสมผล (semantic = เชิงความหมาย)** → เช่น จำนวน = -3 หรือ ส่วนลด = 150% มัน "ถูกชนิด" แต่ "เป็นไปไม่ได้" → **ไม่มี schema ไหนจับได้ ต้องเช็คเอง**
- **กับดักเจ้าปัญหา (bool/int trap):** ใน Python `isinstance(True, int)` ได้ค่า True (เพราะ True/False นับเป็นเลขจำนวนเต็มได้) → ถ้าเช็ค `isinstance(qty, int)` มันจะรับ `True` เป็นจำนวนด้วย! → ต้องใช้ `type(qty) is int` แทน

### Pydantic — เครื่องมือช่วยตรวจ (ไม่ต้องเขียนเอง)
- **Pydantic (ไพแดนติก)** = library ของ Python ที่ให้เรานิยาม "แบบฟอร์ม" ครั้งเดียว แล้วได้ทั้งตัวสร้าง schema และตัวตรวจสอบ (`model_validate_json`) พร้อมบอก error ว่าช่องไหนผิด

### Repair loop (วงจรซ่อม) — ให้ AI แก้งานตัวเอง
- ถ้าตรวจแล้วพัง → **ป้อน error กลับไปบอก AI ให้แก้ แล้วลองใหม่** (จำกัดจำนวนรอบ ~3 ครั้ง กันวนไม่จบ)
- แบ่งเป็น 2 แบบ:
  - **ซ่อมในเครื่องเอง (local repair)** = พังแบบง่ายๆที่แก้เองได้ ไม่ต้องเรียก AI เช่น มี comma เกินท้าย → ลบด้วย regex (การค้นหา/แทนที่ข้อความตามแพตเทิร์น)
  - **ซ่อมด้วยการถาม AI ใหม่ (loop repair)** = พังแบบซับซ้อน → ถาม AI ใหม่ (เสียเวลา+ค่า token)
  - **ลองแบบถูก (local) ก่อนเสมอ**

## 📕 L3 — เซิร์ฟเวอร์หลังบ้าน (Backend)

### ทำไม AI ต้องอยู่หลังเซิร์ฟเวอร์ของเรา?
- **API key (กุญแจ API)** = รหัสลับที่ใช้เรียก AI (และเสียเงินตามการใช้) → **ห้ามให้มันไปอยู่ในเบราว์เซอร์เด็ดขาด** เพราะใครก็ได้เปิดเครื่องมือ developer (dev-tools) ในเบราว์เซอร์แล้ว **ก๊อปกุญแจไปใช้เงินเรา**
- ทางแก้: มี **เซิร์ฟเวอร์ของเราคั่นกลาง** → เบราว์เซอร์คุยกับเซิร์ฟเวอร์เรา, มีแต่เซิร์ฟเวอร์เราที่คุยกับ AI
- ประโยชน์อื่นที่ได้: ตรวจ input ก่อนเสียเงิน · จำกัดจำนวนครั้ง · เก็บ log · ใส่คำสั่งลับ · เปลี่ยนโมเดลได้โดยไม่ต้องแก้หน้าเว็บ (แต่ **ไม่ได้ทำให้ AI คิดเร็วขึ้น**)

### เซิร์ฟเวอร์คืออะไร + HTTP คืออะไร
- **เซิร์ฟเวอร์ = โปรแกรมที่เปิดค้างตลอด** คอยรับ "คำขอ (request)" แล้วส่ง "คำตอบ (response)" กลับ 1 อันต่อ 1 คำขอ
- **HTTP (HyperText Transfer Protocol = โพรโทคอลรับส่งข้อมูลบนเว็บ)** = ภาษากลางที่เบราว์เซอร์กับเซิร์ฟเวอร์ใช้คุยกัน จริงๆแล้วมันก็แค่ **ข้อความธรรมดา** เช่น
  - คำขอ: `POST /api/chat` + ข้อมูล `{"message": "สวัสดี"}`
  - คำตอบ: `200 OK` + `{"reply": "สวัสดีครับ"}`

### REST — วิธีออกแบบ API (verb + status code)
- **REST (Representational State Transfer = สไตล์การออกแบบ API แบบหนึ่ง)** = เอา "สิ่งของ (resource)" ไปวางไว้ที่ URL แล้วใช้ **คำกริยา (verb)** บอกว่าจะทำอะไร
- **Verb (คำกริยา HTTP):**
  - **GET (เก็ต)** = อ่านข้อมูล (ไม่มีผลข้างเคียง ทำซ้ำได้)
  - **POST (โพสต์)** = สร้าง/สั่งทำงาน (มีผลข้างเคียง) → **แชตใช้ POST** เพราะเสีย token = มีผลข้างเคียง
  - PUT/PATCH = แก้ไข · DELETE = ลบ
- **Status code (รหัสสถานะ) = ตัวเลขบอกว่าเกิดอะไรขึ้น** (ดูตารางเต็มในหัวข้อ Quick Reference):
  - **2xx = สำเร็จ** (200 = OK)
  - **4xx = ผู้ใช้/ลูกค้าผิด** — **422** (ส่ง JSON มาถูกแต่ข้อมูลในช่องผิด), **429** (เรียกบ่อยเกินโดนจำกัด), 400 (ข้อมูลพังจริงๆ), 401 (ไม่มีสิทธิ์), 404 (หาไม่เจอ)
  - **5xx = เซิร์ฟเวอร์/เราผิด** — **500** (บั๊กในโค้ดเรา), **502** (AI ที่เราไปเรียกมันพัง), **504** (AI ตอบช้าเกินจนหมดเวลา)

### Pydantic ที่ขอบเซิร์ฟเวอร์ → error 422 อัตโนมัติ
- เราใช้ Pydantic นิยาม "แบบฟอร์มคำขอ" เช่น "message ต้องยาว 1–2000 ตัวอักษร" → ถ้าผู้ใช้ส่งผิด **เซิร์ฟเวอร์ปฏิเสธที่ขอบทันที ก่อนโค้ดเราจะทำงาน = ได้ 422** พร้อมบอกว่าช่องไหนผิด
- หน้าตา error ต่างกัน: **422 = list ของ error หลายช่อง**; error ที่เราสั่งเอง = **ข้อความเดียว** (frontend เอาไปแยกแสดงผลได้)

### สถาปัตยกรรม 3 ชั้น: router → service → repository (แบ่งงานให้เป็นระเบียบ)
เหมือนร้านอาหารแบ่งหน้าที่: พนักงานรับออเดอร์ → พ่อครัว → คลังวัตถุดิบ
- **router (เราเตอร์) = พนักงานรับออเดอร์** — จัดการเรื่อง HTTP อย่างเดียว (รับคำขอ, ส่ง status code) ไม่คิดงานเอง
- **service (เซอร์วิส) = พ่อครัว** — ตรรกะจริงอยู่ตรงนี้ (ประกอบข้อความ, เรียก AI, จำกัดจำนวนครั้ง, เก็บ log)
- **repository (รีโพซิทอรี) = คลังวัตถุดิบ** — ติดต่อฐานข้อมูลอย่างเดียว ไม่มีตรรกะธุรกิจ
- ข้อดี: **ทดสอบตรรกะ (พ่อครัว) ได้โดยไม่ต้องเปิดเซิร์ฟเวอร์จริง**
- **ใครควรปฏิเสธข้อความยาวเกิน?** → **router/ขอบ (Pydantic)** ไม่ใช่ service/repository

### ฐานข้อมูล + คำที่เกี่ยวข้อง
- **Database (ฐานข้อมูล) = ที่เก็บข้อมูลถาวร** (เช่น ประวัติแชต)
- **ORM (Object-Relational Mapping = การจับคู่ตารางฐานข้อมูลกับออบเจกต์ในโค้ด)** = เครื่องมือที่ทำให้เราจัดการข้อมูลในฐานข้อมูลเหมือนจัดการตัวแปรในโค้ด ไม่ต้องเขียนภาษา SQL ดิบ (**SQL = Structured Query Language = ภาษาสอบถามฐานข้อมูล**) · ตัวที่ใช้ชื่อ **SQLAlchemy**
- **async (อะซิงโครนัส = ทำงานแบบไม่รอ)** — เซิร์ฟเวอร์มี "คิวงานเดียว" คอยเสิร์ฟทุกคน; ถ้ามีงานหนึ่งไป "รอ" AI นานๆแบบบล็อกคิว คนอื่นจะค้างหมด → ใช้แบบ async (สั่งแล้วไปทำอย่างอื่นก่อน) เพื่อให้คิวว่างเสิร์ฟคนอื่นได้

### Alembic — การเปลี่ยนโครงสร้างฐานข้อมูลอย่างปลอดภัย
- **Migration (การย้าย/อัปเดตโครงสร้างฐานข้อมูล)** = สคริปต์เล็กๆที่ **มีเวอร์ชัน + เรียงลำดับ + ย้อนกลับได้** (versioned/ordered/reversible) → **ห้ามไปแก้ตารางจริงด้วยมือ**
- **Alembic (อะเลมบิก)** = เครื่องมือทำ migration; 2 ขั้นเวลาเพิ่มคอลัมน์: (1) สร้าง migration ใหม่ (2) **`alembic upgrade head`** (อัปเดตทุกเครื่องให้เป็นโครงสร้างล่าสุด)

### กันเรื่องอื่นๆ
- **CORS (Cross-Origin Resource Sharing = การอนุญาตให้เว็บคนละที่มาเรียกกันได้)** = ปกติเบราว์เซอร์บล็อกการเรียก API ข้ามเว็บ; ถ้าเรา serve หน้าเว็บกับ API จาก **ที่เดียวกัน (origin เดียวกัน)** ก็ไม่ต้องยุ่งกับ CORS
- **Rate limit (การจำกัดอัตราการเรียก) แบบ token bucket (ถังโทเคน):** แต่ละคนมี "ถัง" ที่เติมสิทธิ์ทีละนิดตามเวลา (เช่น 30 ครั้ง/นาที); เรียก 1 ครั้งใช้ 1 สิทธิ์; ถังหมด → **429** (+ header `Retry-After` บอกว่าให้รอกี่วินาที)
- **Idempotency key (กุญแจกันทำซ้ำ):** POST เสียเงิน → ถ้าเน็ตหลุดแล้วส่งซ้ำอาจโดนคิดเงิน 2 รอบ → ให้ผู้ใช้แนบ "รหัสไม่ซ้ำ" มาด้วย เซิร์ฟเวอร์จำผลไว้ ส่งซ้ำรหัสเดิม = คืนผลเดิม ไม่เรียก AI ซ้ำ
- **การทดสอบ (testing) 3 แบบ:** **unit test** (ทดสอบชิ้นส่วนเล็กๆ, ปลอม AI ไว้) · **e2e test** (end-to-end = ทดสอบทั้งเส้นทาง, ปลอม AI) · **eval** (ประเมินคุณภาพคำตอบ AI จริง ใน L8)
  - AI ตอบไม่เหมือนเดิมทุกครั้ง → **ทดสอบว่า "คำตอบมีคำว่า 96 ไหม" (คุณสมบัติ) ไม่ใช่ "คำตอบ = ข้อความนี้เป๊ะ" (equality)**

## 📓 L4 — หน้าจอผู้ใช้ + ทำให้คำตอบพิมพ์ออกมาทีละคำ

### Reactivity (การตอบสนองอัตโนมัติของหน้าจอ)
- **Reactivity** = พอเรา **เปลี่ยนค่าตัวแปร (state = สถานะ)** หน้าจอ **อัปเดตเองอัตโนมัติ** โดยเราไม่ต้องไปสั่งวาดหน้าจอเอง → เหมือนสูตรใน Excel ที่พอเปลี่ยนตัวเลขในช่อง ผลลัพธ์ก็เปลี่ยนตาม
- ตัวอย่าง: มีตัวแปร `reply` (คำตอบ) พอเราเติมคำเข้าไป (`reply += คำ`) ข้อความบนจอก็โตขึ้นทีละคำเอง
- **กับดักที่พังบ่อยสุด:** ต้อง **"สร้างค่าใหม่แล้วกำหนดทับ" (reassign) ไม่ใช่ "แก้ของเดิม" (mutate)** → ใช้ `messages = [...messages, x]` (สร้าง list ใหม่) ไม่ใช่ `messages.push(x)` (แก้ของเดิม ซึ่งหน้าจอจะไม่อัปเดต)
- ศัพท์เสริม: `$state` (ตัวแปรที่หน้าจอตามดู), `$derived` (ค่าที่คำนวณจาก state), `$effect` (สั่งทำงานเสริมหลังหน้าจออัปเดต เช่น เลื่อนจอลงล่างสุด)

### ปัญหา: รอทั้งก้อนแล้วค่อยโผล่ = ผู้ใช้เบื่อ
- ถ้ารอ AI พิมพ์จบ 300 คำก่อนค่อยแสดง (ใช้ `await res.json()`) → ผู้ใช้เห็นวงกลมหมุนๆ 8 วิ แล้วข้อความค่อยโผล่มาทีเดียว
- **ทางแก้ = streaming (ส่งทีละคำ)** → เวลารวมเท่าเดิม (8 วิ) แต่เห็นคำแรกใน ~0.2 วิ → "รู้สึก" เร็วกว่ามาก + กด Stop ได้

### SSE คืออะไร (พระเอกของบทนี้)
- **SSE (Server-Sent Events = เหตุการณ์ที่เซิร์ฟเวอร์ส่งมา)** = วิธีที่เซิร์ฟเวอร์ **"ส่งข้อมูลมาให้เบราว์เซอร์ทางเดียวเรื่อยๆ"** ผ่าน HTTP ธรรมดา → เหมาะกับการส่ง token ทีละตัวสุดๆ
- เทียบกับตัวเลือกอื่น:
  - **plain fetch (การขอข้อมูลธรรมดา)** = ขอ 1 ครั้งได้คำตอบทั้งก้อน (ไม่ส่งทีละชิ้น)
  - **WebSocket (เว็บซ็อกเก็ต)** = ช่องทางคุยกัน **2 ทาง** (ทั้งส่งและรับพร้อมกัน) → ใช้กับห้องแชต/เกมออนไลน์ แต่ **หนักและซับซ้อนกว่า**
  - **SSE = ทางเดียว (เซิร์ฟเวอร์→เบราว์เซอร์)** → แชตที่เซิร์ฟเวอร์ป้อนคำตอบมาให้ ใช้แค่ทางเดียวก็พอ → **เลือก SSE เพราะง่ายกว่า**

### รูปแบบข้อมูลของ SSE (text/event-stream)
- Header (ส่วนหัวคำตอบ) ต้องเป็น **`Content-Type: text/event-stream`** (บอกเบราว์เซอร์ว่านี่คือสตรีม)
- แต่ละเหตุการณ์ (event) เขียนเป็น `data: <ข้อความ>` แล้ว **จบด้วยบรรทัดว่าง (`\n\n` = ขึ้นบรรทัดใหม่ 2 ที)** → บรรทัดว่างคือสัญญาณว่า "event นี้จบแล้ว ส่งได้"
- ตอนจบสตรีมส่ง **`data: [DONE]`** (เป็นข้อตกลงกันว่าแปลว่า "หมดแล้ว" — เบราว์เซอร์เห็นแล้วรู้ว่าหยุด ไม่ต้องรอสายหลุด)

### 2 กับดักของ SSE (ออกสอบแน่ๆ)
1. **กับดักขึ้นบรรทัดใหม่ (newline trap):** ถ้าคำที่ AI ส่งมาคือตัว "ขึ้นบรรทัดใหม่" เอง (`\n`) → มันจะทำให้ event จบก่อนเวลา สตรีมพัง → **แก้โดยห่อทุกคำเป็น JSON** (`data: {"token": "..."}`) เพื่อให้ payload เป็น "บรรทัดเดียวเสมอ" ไม่ว่าข้างในจะมีอะไร (ต้องใช้ `json.dumps` ไม่ใช่การพิมพ์แบบ repr ที่ได้ single-quote ผิดรูป JSON)
2. **กับดักข้อมูลมาไม่ตรงชิ้น (buffer trap):** เน็ตส่งข้อมูลมาเป็นก้อนๆ **ไม่ตรงกับขอบของ event** — อ่าน 1 ครั้งอาจได้ครึ่ง event หรือได้ 3 event รวดเดียว → ต้อง **เก็บพักไว้ใน buffer (บัฟเฟอร์ = ที่พักข้อมูลชั่วคราว), ตัดตรงบรรทัดว่าง `\n\n`, และเก็บชิ้นท้ายที่ยังไม่ครบไว้** รอต่อกับก้อนถัดไป
- **ฝั่งฟรอนต์:** ถ้าเผลอเอาข้อมูลดิบมาต่อกันตรงๆ (`reply += value` โดยไม่ตัด `\n\n`) → จะเห็นคำว่า `data:` และ `[DONE]` โผล่ในคำตอบ + event ที่คร่อม 2 การอ่านจะพัง

### เรื่องเพิ่มเติมของ SSE (มีในโน้ต ออกได้)
- **EventSource** = ตัวอ่าน SSE สำเร็จรูปในเบราว์เซอร์ (จัดการ event + ต่อสายใหม่อัตโนมัติผ่าน `Last-Event-ID`) **แต่มันขอได้แค่แบบ GET ส่ง body ยาวๆไม่ได้** → แชต (ข้อความยาว) ต้อง POST → เลยใช้ fetch-reader เขียนเองแทน (ซึ่งไม่ต่อสายอัตโนมัติ)
- **Heartbeat (การเต้นของหัวใจ = สัญญาณคงสาย):** ถ้า AI "คิด" นานก่อนตอบ สายอาจถูกตัดเพราะเงียบเกินไป → ส่งบรรทัดที่ขึ้นต้นด้วย `:` (คือ **comment/หมายเหตุ** ที่เบราว์เซอร์เมิน) ทุก ~15 วิ เพื่อให้สายยังมีการเคลื่อนไหว ไม่โดนตัด
- **Error frame (เฟรมแจ้ง error):** ถ้า AI พังกลางทาง (ตอนที่ส่ง status 200 ไปแล้ว) จะส่ง 500 ไม่ได้ → ส่ง `data: {"error": ...}` แทน
- **การหยุดกลางคัน:** ใช้ **AbortController (ตัวยกเลิก)** สั่ง `abort()`; ฝั่งเซิร์ฟเวอร์ต้องเช็ค `is_disconnected()` ด้วย ไม่งั้นมันจะสร้าง (และคิดเงิน) ต่อทั้งที่ไม่มีคนอ่านแล้ว
- **`fetch` แจ้ง error เฉพาะตอนเน็ตหลุด** — ถ้าเซิร์ฟเวอร์ส่ง 500 มันไม่ถือว่า error → ต้องเช็ค `res.ok` เอง

### ปัญหาคลาสสิกตอนขึ้นจริง: "localhost ทำงาน แต่ deploy แล้วมาทีเดียว"
- สาเหตุคือ **reverse proxy (พร็อกซีตัวกลาง เช่น nginx, Cloudflare)** ที่คั่นอยู่ มัน **กักข้อมูลรอเป็นก้อนใหญ่ (buffering)** แล้วค่อยปล่อย → ทำให้ streaming เสีย → แก้ด้วยการตั้ง header `X-Accel-Buffering: no` + ปิดการบีบอัด (compression) บนสตรีม
- **CDN (Content Delivery Network = เครือข่ายกระจายเนื้อหา เช่น Cloudflare)** ก็กักข้อมูลได้เหมือนกัน

## 📔 L5 — คลังความรู้ที่ค้นหา "ความหมาย" ได้ (Vector Storage)

### ปัญหา: AI ไม่รู้เรื่องเอกสารของเรา + ค้นด้วยคำตรงๆไม่พอ
- AI รู้แค่สิ่งที่มันเทรนมา — ไม่รู้จักเอกสาร/PDF/โน้ตของเรา
- **ค้นด้วยคำ (keyword search) ไม่พอ:** ถามว่า "รีเซ็ตรหัสผ่านยังไง" แต่เอกสารเขียนว่า "เปลี่ยนข้อมูลล็อกอิน" → ไม่มีคำตรงกันเลย หาไม่เจอ → เราต้องการการค้นที่เข้าใจ **"ความหมาย"**

### Embedding — แปลงข้อความเป็น "พิกัดของความหมาย"
- **Embedding (เอ็มเบดดิง = การฝังความหมายลงในตัวเลข)** = แปลงข้อความ 1 ชิ้นเป็น **vector (เวกเตอร์ = ชุดตัวเลขความยาวคงที่)** เช่น 1024 ตัวเลข
- **ข้อความที่ความหมายใกล้กัน → พิกัดอยู่ใกล้กัน** → เหมือนแผนที่ที่ "สัตว์" อยู่โซนเดียวกัน "รถ" อยู่อีกโซน
- **โมเดล embedding ของคลาสชื่อ bge-m3** ให้ vector ขนาด **1024 ตัวเลข** และรองรับหลายภาษา (อังกฤษ+ไทย) → ถามอังกฤษหาเอกสารไทยได้!
- **แบบของเล่น (bag-of-words = ถุงคำ):** แค่นับจำนวนคำ → "cat" กับ "kitten" ไม่มีคำร่วม = คะแนน 0 (แม้จะเรื่องแมวเหมือนกัน); **โมเดลจริง**เข้าใจว่าลูกแมวคือแมว

### Cosine similarity — วัดว่า 2 พิกัดชี้ไปทางเดียวกันแค่ไหน ⭐ (ข้อคำนวณเดียวของวิชา)
- **Cosine similarity (โคไซน์ ซิมิลาริตี้ = ความคล้ายเชิงมุม)** = วัด **"มุม" ระหว่าง 2 เวกเตอร์ ไม่ใช่ระยะทาง** — ชี้ทางเดียวกัน = คล้าย ไม่ว่าจะยาวสั้นแค่ไหน
- สูตร: `cos(a,b) = (a·b) / (‖a‖ × ‖b‖)` โดย `a·b` = ผลคูณจุด (dot product = จับคู่คูณกันแล้วบวก), `‖a‖` = ความยาวเวกเตอร์ (norm = √ผลบวกกำลังสอง)
- **ค่าออกมา: +1 = เหมือน (ทางเดียวกัน), 0 = ไม่เกี่ยวกัน (ตั้งฉาก), −1 = ตรงข้าม** · เพื่อนบ้านที่ใกล้ที่สุด = ค่าสูงสุด
- **ตัวอย่างต้องทำเป็น (จำได้เลย):** a=[1,0,1], b=[1,1,0]
  - ผลคูณจุด = (1×1)+(0×1)+(1×0) = **1**
  - ความยาว: ‖a‖ = √(1+0+1) = √2 ; ‖b‖ = √(1+1+0) = √2
  - cosine = 1 ÷ (√2 × √2) = **1/2 = 0.5** (มุม 60°)
- โมเดลจริง: แม้ประโยคไม่เกี่ยวกันก็ยังได้ ~0.3–0.5 (ไม่ 0) → **ให้ "จัดอันดับเอาสูงสุด" อย่าไปตั้งเส้นตายค่าดิบ**

### เก็บ vector ไว้ที่ไหน + ค้นเร็วยังไง (vector index)
- ค้นแบบดิบ (brute-force = ไล่เทียบทุกตัว, ชื่อทางการ **kNN = k-Nearest Neighbors = k เพื่อนบ้านใกล้สุด**) — โอเคถ้ามีไม่กี่หมื่นชิ้น
- ถ้าเยอะเป็นล้าน → ใช้ **ANN (Approximate Nearest Neighbor = การหาเพื่อนบ้านใกล้สุดแบบประมาณ)** = ยอมพลาดนิดหน่อยเพื่อความเร็ว (2 แบบ: HNSW แบบกราф, IVFFlat แบบจับกลุ่ม)
- **pgvector (พีจีเวกเตอร์)** = ส่วนเสริมของฐานข้อมูล **Postgres** ที่เก็บ vector ได้ → ค้นด้วยคำสั่ง SQL ปกติ
  - **⚠️ กับดัก:** เครื่องหมาย **`<=>` ของ pgvector คือ "ระยะทาง (distance)" ไม่ใช่ความคล้าย** → **ยิ่งน้อยยิ่งใกล้** → ต้องเรียง **ASC (จากน้อยไปมาก)** · ถ้าใช้ความคล้าย (cosine similarity) ยิ่งมากยิ่งดี → เรียง DESC · **ใส่ผิดทาง = ได้ผลแย่สุดขึ้นก่อน**

### Chunking — หั่นเอกสารเป็นชิ้น + ติดป้าย (metadata)
- **ไม่ embed ทั้ง PDF เป็นก้อนเดียว** → ต้อง **หั่นเป็นชิ้น (chunk = ท่อน/ชิ้นข้อความ)** เพราะถ้าก้อนใหญ่ vector จะ "เบลอ" เหมือนถ่ายเฉลี่ยทั้งหน้า จับอะไรก็ได้จางๆ
- **ขนาดที่ดี: ~200–500 token ต่อชิ้น + ให้ชิ้นซ้อนกันนิด (overlap) ~10–20%** เพื่อไม่ให้ประโยคขาดตรงรอยตัด
- **Metadata (เมทาดาต้า = ข้อมูลกำกับ)** = ป้ายที่แปะไว้กับแต่ละชิ้น เช่น ชื่อไฟล์, เลขหน้า → ใช้ทำ 2 อย่าง: (1) **อ้างอิงแหล่ง (citation)** บอกว่าเอามาจากไฟล์ไหนหน้าไหน (2) **กรองก่อนค้น (filter)** เช่น ค้นเฉพาะบทที่ 5
- **กฎเหล็ก: ต้อง embed คำถามกับเอกสารด้วยโมเดลตัวเดียวกันเสมอ** — คนละโมเดล = พิกัดคนละแผนที่ เทียบกันไม่ได้ (ศัพท์: space mismatch = พิกัดคนละสเปซ) → **นี่คือบั๊กที่พังบ่อยสุด**
- **มิติของ vector ล็อกตามโมเดล:** bge-m3 = 1024, OpenAI (text-embedding-3-small) = 1536, MiniLM (รันในเครื่อง) = 384 → ผสมกันไม่ได้

## 📒 L6 — RAG: เอาคลังความรู้มาช่วย AI ตอบ (แกนของทั้งวิชา)

### RAG คืออะไร แก้ปัญหาอะไร
- **RAG (Retrieval-Augmented Generation = การสร้างคำตอบโดยเสริมด้วยการค้นคืน)** = **"ค้นก่อน แล้วค่อยอ่านตอบ"** (retrieve-then-read)
- ปัญหา: ถาม AI เรื่องเอกสารเรา มันจะ **มั่วอย่างมั่นใจ** (เพราะมันไม่รู้จริง) → RAG แก้โดย **หาข้อมูลจริงจากคลังเราก่อน แล้วยัดใส่ให้ AI อ่านตอนตอบ**
- ได้ 3 อย่าง: (1) **grounding = ยึดกับข้อมูลจริง** (2) หลอนน้อยลง (3) **อ้างอิงแหล่งได้ (citation)**

### RAG vs Fine-tuning (2 วิธีสอนความรู้ใหม่ให้ AI)
- **Fine-tuning (ไฟน์จูน = การฝึกโมเดลเพิ่ม)** = "อบ" ความรู้เข้าไปในตัวโมเดลเลย → **แพง ช้า และตกยุคทันทีที่ข้อมูลเปลี่ยน** (แก้เอกสาร 1 บรรทัด = ต้องฝึกใหม่หมด)
- **RAG** = เก็บความรู้ไว้นอกโมเดล อัปเดตเมื่อไหร่ก็ได้ → แก้เอกสารแล้วทำ index ใหม่ คำตอบถัดไปสดทันที ถูกกว่า ตรวจสอบได้ อ้างอิงได้
- **ข้อมูลที่เปลี่ยนบ่อย/เป็นความลับ → ใช้ RAG**

### ขั้นตอน RAG ตอนถาม (retrieve-then-read)
1. แปลงคำถามเป็น vector (embed the question)
2. ค้นหา chunk ที่ใกล้ที่สุด k ชิ้น (search top-k)
3. ยัด chunk พวกนั้นเข้าไปใน prompt เป็น "บริบท (context)"
4. ให้ AI ตอบโดยอิงบริบทนั้น
- **AI อ่านแค่ chunk ไม่กี่ชิ้นที่ค้นเจอ — ไม่เคยเห็นเอกสารทั้งหมด** → คุณภาพขึ้นกับ **การค้น (retrieval) เป็นหลัก** โมเดลเป็นรอง

### การประกอบ prompt + การอ้างอิง (citation)
- เขียน prompt ว่า: **"ตอบโดยใช้เฉพาะบริบทข้างล่างนี้ ถ้าไม่มีให้บอกว่าไม่รู้"** + ใส่ chunk ที่เลขกำกับ `[1] {ข้อความ} (ที่มา)` + คำถาม + "อ้างอิงเป็น [1], [2]"
- **"ใช้เฉพาะบริบท" + "ถ้าไม่มีให้บอกว่าไม่รู้" = 2 ประโยคคุมการหลอน** + ตั้ง temperature=0
- ต้อง **เก็บ metadata (ที่มา) ตั้งแต่ตอนทำ index** ไม่งั้นอ้างอิงไม่ได้ (จะอ้างอิงสิ่งที่ไม่ได้เก็บไว้ไม่ได้)

### min_score — เส้นตายความมั่นใจ + ทางออก "ไม่รู้"
- **min_score (คะแนนขั้นต่ำ)** = ถ้าคะแนนความคล้ายต่ำกว่านี้ (เช่น 0.45) แปลว่าอ่อน → ทิ้ง
- **ถ้าไม่มี chunk ไหนผ่านเส้น → ตอบ "หาไม่เจอในเอกสาร" ไปเลย ไม่ต้องเรียก AI** (กันมันมั่ว)

### ⭐⭐ บันไดแก้บั๊ก RAG (Debug Ladder) — ออกหนักสุด!
เวลา RAG ตอบผิด **ให้ไล่ตามลำดับนี้ ดูข้อมูลทุกจุด อย่าเริ่มโทษที่ตัว AI:**
1. **chunk ที่ควรเจอ ถูกค้นเจอไหม?** → พิมพ์ดู top-k → ถ้าไม่เจอ = ปัญหาการค้น ไม่ใช่ AI
2. **มันอยู่ใน index ไหม?** → index เก่า/หั่นแย่ → ทำ index ใหม่
3. **คำไม่ตรง (vocabulary mismatch)?** → ค้นด้วยคำตรงๆพลาด synonym → เปลี่ยนไปใช้ embedding
4. **ค้นเจอแล้วแต่ AI มองข้าม?** → **"หายไปตรงกลาง" (lost in the middle)** → ลด k ให้เหลือน้อย + เอา chunk ดีที่สุดไว้ต้น
5. **ค้นดีแล้วแต่ยังมั่ว?** → prompt "ใช้เฉพาะบริบท" + ให้บอก "ไม่รู้" + temperature=0
- **สิ่งแรกที่ต้องทำเสมอ: พิมพ์ดู chunk ที่ค้นเจอ** (ไม่ใช่ปรับ temperature หรือเปลี่ยนโมเดลใหญ่ขึ้น)

### อาการพัง (failure modes) อื่นๆ
- **Bad chunks (ชิ้นแย่)** = ค้นได้ชิ้นผิด/ครึ่งๆ → ขยะเข้า ขยะออก
- **Lost in the middle (หายตรงกลาง)** = AI สนใจต้นกับท้ายบริบทดีกว่าตรงกลาง → **k=40 มักแย่กว่า k=4** (ข้อมูลจริงจมในกองขยะ) → **ใช้ k น้อยๆ 3–5, chunk ดีที่สุดไว้ขอบ**
- **Nothing relevant (ไม่มีข้อมูล)** + prompt อ่อน → มั่ว → ต้องมี "ให้บอกว่าไม่รู้"
- **Stale index (index เก่า)** = เอกสารเปลี่ยนแต่ยังไม่ทำ index ใหม่
- **Query rewrite (เขียนคำถามใหม่ก่อนค้น):** คำถามพูดแบบคุยเล่น/มีคำสรรพนาม ("มัน", "อันนั้น") → ค้นไม่เจอ → **เขียนใหม่ให้ตรงคีย์เวิร์ด + แทนคำสรรพนาม** ก่อนค้น
- **Dedupe (กำจัดชิ้นซ้ำ):** chunk ซ้ำๆกันแย่ง slot → ทิ้งตัวซ้ำก่อนประกอบ prompt
- **อ้างอิงผิดเลข [n]** = บั๊กที่ตอน**ประกอบ prompt** ไม่ใช่ตอนค้น

## 🎯 Quick Reference — ตารางท่องก่อนเข้าห้องสอบ
| เรื่อง | สรุปสั้นๆ |
|--------|-----------|
| **AI ทำอะไร** | เดาคำถัดไป; ไม่มีความจำ (stateless) ต้องส่ง history ใหม่ทุกครั้ง |
| **temperature** | 0 = ตอบนิ่งเหมือนเดิม; ปรับ temperature **หรือ** top_p อย่างเดียว |
| **streaming** | แค่ "รู้สึก" เร็ว (perceived latency) ไม่ได้เร็วขึ้นจริง |
| **JSON mode** | รับประกันแค่ไวยากรณ์ ไม่ใช่รูปร่าง; proxy คลาสเมินคำสั่งนี้ |
| **validation** | ใช้ json.loads (ห้าม eval); `type()` ไม่ใช่ `isinstance` (กับดัก bool); ความสมเหตุสมผล ≠ ชนิด |
| **status code** | **422** ช่องข้อมูลผิด · **429** เรียกบ่อยเกิน(+Retry-After) · **502** AI พัง · **504** AI ช้าเกิน |
| **verb** | แชต = **POST** (มีผลข้างเคียง เสีย token) |
| **3 ชั้น** | router (รับออเดอร์/HTTP) → service (ตรรกะ) → repository (ฐานข้อมูล) |
| **Alembic** | เปลี่ยนโครงสร้างฐานข้อมูล: มีเวอร์ชัน/เรียงลำดับ/ย้อนได้; **upgrade head** |
| **SSE** | ส่งทางเดียว; `text/event-stream`, `data:`, บรรทัดว่าง `\n\n`, **[DONE]**; ห่อ token เป็น JSON กันบรรทัดใหม่; เก็บ buffer กันชิ้นไม่ครบ |
| **reactivity** | เปลี่ยน state → จออัปเดตเอง; ต้อง **สร้างใหม่แล้วกำหนดทับ** `[...arr, x]` (ไม่ใช่ `.push`) |
| **cosine** | วัดมุม; **+1/0/−1**; `cos([1,0,1],[1,1,0]) = 0.5` |
| **pgvector `<=>`** | คือ "ระยะทาง" น้อย=ใกล้ → เรียง **ASC** |
| **chunk** | 200–500 token, ซ้อน 10–20%, ติด metadata; **embed คำถาม+เอกสารด้วยโมเดลเดียวกัน** |
| **RAG** | ค้นก่อน-อ่านตอบ; อ่านแค่ top-k; RAG > fine-tune (ไม่ต้องฝึกใหม่ + อ้างอิงได้) |
| **min_score** | ต่ำกว่าเส้น → ตอบ "ไม่รู้" |
| **debug RAG** | **พิมพ์ดู top-k ก่อนเสมอ**; หายตรงกลาง → k น้อย, ชิ้นดีไว้ต้น |
